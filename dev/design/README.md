# 小组件视觉方案

`mock.html` 是三版方案的静态样张，用无头 Chrome 渲染成 `mock.png`：

```sh
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --disable-gpu --screenshot=mock.png \
  --window-size=1300,2450 --hide-scrollbars --force-device-scale-factor=2 mock.html
```

`compare.html` / `compare.png` 是只含中小尺寸的对照图。

## 为什么用 HTML 打样而不是直接改 widget.tsx

真机是唯一的渲染事实，但一轮真机验证的成本是「改代码 → 发版 → 手机更新 → 看」。
配色和排版这种需要来回比较的事，用 HTML 先收敛到一版，再一次性搬进 TSX，
省掉大部分往返。**样张不能替代真机验证，只能减少次数。**

## 深浅色怎么适配

不用 `{light, dark}` 动态色，也不用 `"secondaryLabel"` 这类语义色——两者在这个
小组件里都没验证过，而且曾经和「一片漆黑」搅在一起分不清。

改用 `Device.colorScheme`（TS 版 Device API 里文档化的，返回 `"light"` / `"dark"`），
渲染时读一次，从两套**扁平 hex** 里选一套。背景自己画，前景对比度就完全可控。

## 配色是校验过的，但校验的是正确的那一项

先用 dataviz 的分类调色板校验器跑，结果 FAIL：警告色和危险色在色觉障碍下
ΔE 只有 2.8。但那个校验器的 scope 写着「仅限分类调色板；单独的状态/文字色
应当查 WCAG 文字对比度」——状态色不是分类色，它有二重编码（数字本身、条长）。

所以按 WCAG 文字对比度重新查，并把警告色和危险色拉开：

| | 日间 | 夜间 |
| --- | --- | --- |
| good | `#15803D` | `#4ADE80` |
| warn | `#A16207` | `#F5C451` |
| bad  | `#BE123C` | `#FF8080` |

六种表面下全部 ≥ 4.5:1。三级文字（时间戳）也从 2.4 提到 3.3 以上。

**教训：校验器报 FAIL 时，先确认它检查的是不是你这件事。** 硬凑一组能过分类
校验的状态色，反而会牺牲「红=危险、黄=警告」这个更重要的约定。


## 多窗口怎么排（multi.html / multi.png）

Claude 一个账户就有 5h / 7d / 7d Opus 三个窗口，Codex 两个，而 DeepSeek 只有一个余额。
「一行一账户」在这种不对称下会塌掉，所以给方案 C 出了三个变体：

| 变体 | 做法 | 代价 |
| --- | --- | --- |
| C-1 | 每个窗口独立一行，账户名作为分组标题 | 最直白，每个窗口都有自己的刻度；中尺寸只放得下 2 个账户 |
| C-2 | 一行一账户，数值横向并列，刻度线按窗口分段 | 一屏账户最多；窗口多时每个数字都变小 |
| C-3 | 只放大「最该操心的那个窗口」，其余降级成一行小字 | 一屏账户较多且主次分明；次要窗口没有刻度 |

**选择依据不是好看，是「一眼要回答什么问题」：**
- 想知道「每个窗口分别还剩多少」→ C-1
- 想知道「哪些账户还宽裕」→ C-2
- 想知道「现在最该操心什么」→ C-3

C-3 的排序键是各窗口里最紧张的那个（`worst()`），所以大数字天然就是要看的那个。


## 最终选定：方案 B-2（终端 · 树形连线）

`termB.html` / `termB.png` 是 B 的三个多窗口变体。选 B-2 的理由：

Claude 一个账户有 5h / 7d / 7d Opus，Codex 两个，DeepSeek 只有一个余额。
终端本来就有表达这种层级的惯用法——`├ └` 连线，一眼看得出谁属于谁。
B-1（缩进续行）在账户名长时会撞列；B-3（主窗口 + 摘要）把次要窗口降级得太狠。

只有一个指标的账户不画树线，直接和账户名同行——省一行，也避免为了形式而形式。

### 等宽排版的命门是列宽

中文账户名是**双宽字符**，用 `String.length` 补空格会整体错位，而错位在等宽
排版里特别刺眼，一眼毁掉整块。所以补齐全走 `app/term.ts` 的 `padEnd/padStart`，
它按 East Asian Width 算列数，`dev/test_logic.mjs` 里有断言钉住。

### 为什么用 styledText 而不是几个 Text 拼

一行里要给「窗口名 / 进度条 / 数值」分别上色。用 HStack 拼多个 `<Text>` 的话，
HStack 会在片段之间加自己的间距，等宽对齐当场就毁了。`styledText` 的分段形式
把整行当作**一个** Text 渲染，间距完全由字符本身决定。


## 效果图必须由实现代码生成（preview.mjs）

`dev/design/preview.mjs` 生成 `impl.html` / `impl.png`。第一版直接 import `app/term.ts`，
列宽常量从 `widget.tsx` 逐字抄；v0.8.0 起改为打包 `app/layout.ts` 整个调用，见文末。

**这不是形式主义。** 第一版效果图是手写的，我在里面用了 `5h` `7d` `opus` 这种短标签，
看起来很妥。换成实现代码一跑，真实标签是中文的「5 小时」「7 天 Opus」，
立刻露馅：

- 窗口名被截成 `5 …`、`7 天…`、`总余…`
- 中尺寸只放得下 **1 个**账户（`1/6 accounts`）——Claude 一家就吃掉 3 行

两个都是真 bug，而手写的样张把它们藏住了。修法：给指标加一个 `short` 短标签
（`shortLabel()`），并按实际可用列数重算 `LAYOUT`——中尺寸 364pt 减内边距约 334pt，
SF Mono 11pt 步进约 6.6pt，能放约 50 列，我原来只用了 30。

**判据：效果图和交付物如果不是同一套代码算出来的，它就只是一张画。**


## v0.8.0：小、中尺寸重排（layout.ts）

用实现代码生成的效果图暴露了第一版小、中尺寸的两个逻辑问题——不是配色，是**答错了问题**：

- **小尺寸的大字是 `metrics[0]`，不是最紧张的窗口。** 账户因为 Opus 窗口只剩 9% 排到第一，
  大字却写着 5h 窗口的 58%。修法：`AccountRow` 加 `worst`（和排序同一个判据），
  小尺寸、锁屏、汇总统计都改用它。
- **中尺寸用树形，每账户只取前 2 个指标。** Claude 一家吃掉 3 行，6 个账户只显示 2 个；
  被截掉的恰好是最红的 Opus 窗口，底下却写着 `2 alert`——两个 alert 一个都看不见。
  修法：中尺寸改成**表格**（一行一账户，窗口横排），超过 3 个窗口换行续接，不截不挑。
  进度条在这里放不下，状态交给颜色；要看条去大尺寸。

顺手修了列宽估算：SF Mono 步进是 **0.618 em**（从 `SFNSMono.ttf` 的 hmtx 表读的），
11pt 就是 6.8pt，中尺寸 334pt 只放得下 49 列，不是 50。按 50 排的行在真机上会被 SwiftUI
截成「…」。现在的预算：小 20 列、中/大 48 列。

排版逻辑全部搬进 `app/layout.ts`，它不 import "scripting"，所以：

- `preview.mjs` 直接 esbuild 打包它来生成 `impl.html`，连列宽常量都不用抄；样例数据走
  `view.ts` 的 `buildRows`，标签是 provider 真正会给的中文；
- `test_logic.mjs` 对每一行断言「不超过列宽预算」，超了就是真机上会截断的行。

**真机待验证**：行高。列宽是量出来的，行高是按 15–16pt 估的，中尺寸给 6 行内容留了余量。
如果真机上底部状态行下面空得多，`ROWS.medium` 可以提到 7。
